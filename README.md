# DPY Mercantile × Gratek: website prototype v8 ("Mist")

The homepage plus a full set of inner pages (see **The other pages** below).

Modelled on the Fundora landing page:
- a soft, steamy hero
- a thin grey-gradient headline
- floating light cards around a centrepiece
- a coloured brand band that fades to white
- frosted panels on photos
- a three-card plan row

The green is replaced with **DPY's logo colours**:

| Logo part | Used for |
|---|---|
| Drop blues (#013C80 → #0D68C3) | Water, cold, the brand band |
| Gear red (#C70A0E) | Heat, hotspots, the featured buttons |
| Gear black | Type and the primary button |

**Open it:** double-click `index.html`. GSAP, Lenis, Three.js and MapLibre are bundled in `assets/vendor/`. Opened from disk, the 3D borrows Three.js from unpkg, because browsers block local modules on `file://`. Online, everything except the Manrope font, the map tiles and Street View comes from the site itself.

## Testing

Run `npm install` once, then:

- `npm test`: the form sender's 13 unit checks (no browser, nothing is emailed).
- `npm run test:pages`: every browser check in `tools/test/`, against the local site. It starts `wrangler dev` on port 8787 if nothing is running there, and stops it after. It prints only failures and a pass/FAIL line per set, and exits with an error if anything failed. Run it before every PR.
  - `server`: all 107 rules in `_redirects` answer 301 to a page that exists; the repo's own files (config, sources, tests, `node_modules`, `.dev.vars`) answer 404; the form sender refuses GET and other sites.
  - `pages`: every page in `sitemap.xml` at phone, tablet and desktop size: loads, no script errors, no sideways scroll, no text field under 16px on touch screens.
  - `forms`: the homepage, Contact and Service forms on a phone (pinned send button, chat button stepping aside, both sending outcomes, the earliest service day) and their desktop send row.
  - `careers`: Apply, every validation path, the CV box, sending with the CV, and the email fallback.
  - `design`: rules that broke before: the header number on For Business, benefit cards filling their rows, spec tables, the hidden quote bar, one-line Add buttons, small-text contrast.
  - `links`: every link on every page leads to a page that answers, and every link to a #section finds that section.
  - `motion`: page transitions (and none with reduced motion), and iPhone home-bar and notch spacing in portrait and landscape.
- Options: `ONLY=forms,careers` runs some sets; `SHOTS=/some/folder` saves screenshots; `BASE=https://prototype.dpy-mi.workers.dev` checks the live copy.
- First time on a machine: `npx playwright install chromium`. On Linux it also needs `npx playwright install-deps chromium` (admin rights). WebKit (Safari's engine) runs too if installed; otherwise the transition check says it skipped it.

**Not covered by the checks:** a real iPhone or Safari, a real email through Resend, and Cloudflare itself (redirects and caching on the live domain). Those are checked by hand at launch.

## Deploying (Cloudflare Workers)

Live at **https://prototype.dpy-mi.workers.dev**. It is a Cloudflare Worker named `prototype` (account subdomain `dpy-mi`), connected to the GitHub repo markdark09/dpy-prototype. Every push to `main` goes live in about 30 seconds. There's no build step.

- `package.json`: pins Wrangler (4.158.0) and Playwright, so Cloudflare's build and our machines run the same versions. Cloudflare's branch previews (`wrangler preview`) need Wrangler 4.135 or newer installed in the project; without this file every PR build failed. `npm install`, then `npm run dev` (local site and form sender on port 8787), `npm test` (form-sender tests), `npm run build` (regenerates pages, redirects and sitemap). `allowScripts` lets only esbuild and workerd, Wrangler's own parts, run install scripts.
- `wrangler.jsonc`: the Worker name (it must match the dashboard), the folder to serve, `404.html` for unknown paths, and `worker/index.js`, which runs only for `/api/*`. Every other address is served straight from the files.
- `.assetsignore`: files that are not served (this README, the config, `package.json` and its lockfile, `node_modules/`, `src/`, `tools/`, `worker/`, git files, and any local secrets file such as `.dev.vars`). The site is served from the repo root, so anything new at the root must be added here.
- `_headers`: `noindex` for the whole prototype, basic security headers, 30-day caching for `/assets/*`, and `index.html` always fresh.
- `_redirects`: generated by the build (see **Old addresses** below). Don't edit it by hand.
- `sitemap.xml`: generated by the build, with every page at the `SITE` address in `tools/lib.mjs`.
- `404.html`: a branded "page not found" page.
- `robots.txt`: blocks all crawlers (prototype).
- The share-preview tags (Open Graph and Twitter) point to https://prototype.dpy-mi.workers.dev/, so links pasted in Messenger and Viber show `assets/img/og-cover.jpg`.

### The forms send for real (once Resend is set up)

The quote forms (homepage and Contact), the service booking form and the Careers application form post to `/api/send` (`worker/send.js`). It emails DPY's team through [Resend](https://resend.com), the same setup as makarios-it.com. Quote requests, service requests and job applications each go to their own inbox. A job application must include an email and a CV (PDF or Word, up to 5 MB), which arrives as an attachment. The server checks the file's first bytes, not just its name, and cleans the file name. The recipient is fixed on the server, so the endpoint can't be used to email anyone else. The email puts **Call 09XX...** first as a tap-to-call button, because the site promises a call back. Spam is stopped by a hidden field that only bots fill, a same-site check, and an optional limit of 5 requests per visitor per 10 minutes.

**Until it is set up, nothing breaks:** the server answers "not set up" and the page opens the visitor's email app with the request written out, as the prototype always did. The thank-you message says which one happened. The same fallback covers a failed send and a page opened from disk.

So the code can be merged and deployed before any of this is set. Switching it on has two stages, both in Cloudflare > Workers > `prototype` > Settings > Variables and secrets.

**Stage 1, a test (we can do this alone).** Until `dpymi.com.ph` is verified in Resend, Resend only delivers to the Resend account owner's own address. So for a test, send both kinds of request there:

| Name | Type | Value |
|---|---|---|
| `RESEND_API_KEY` | Secret | the Resend key (`re_...`) |
| `QUOTE_TO` | Text | the Resend account's own email |
| `SERVICE_TO` | Text | the Resend account's own email |
| `CAREERS_TO` | Text | the Resend account's own email |

Leave `MAIL_FROM` unset; it defaults to `DPY Website <onboarding@resend.dev>`, which works without a verified domain.

**Stage 2, real delivery (needs DPY).** Whoever manages DNS for `dpymi.com.ph` adds the records Resend gives (DKIM, SPF, return path) to verify the domain. Then change:

| Name | Type | Value |
|---|---|---|
| `QUOTE_TO` | Text | `sales@dpymi.com.ph` (must exist as a mailbox or forward) |
| `SERVICE_TO` | Text | `service@dpymi.com.ph` (must exist as a mailbox or forward) |
| `CAREERS_TO` | Text | `careers@dpymi.com.ph` (must exist as a mailbox or forward) |
| `MAIL_FROM` | Text | `DPY Website <website@dpymi.com.ph>` |

Optional: bind a KV namespace as `RATE_LIMIT` to turn on the per-visitor limit. `keep_vars` in `wrangler.jsonc` stops a deploy from wiping these.

Tests: `node --test worker/send.test.mjs` (13 checks). They stand in for Resend's replies, so nothing is sent; a real email has not gone through yet. Stage 1 above is that check.

### Old addresses

`_redirects` sends every address the WordPress site at dpymi.com.ph had (both of its sitemaps and its menu: 48 addresses) to the page that replaces it, with a permanent (301) redirect. For example, `/product/aquapower-s35m/` goes to `/products/aquapower-s35m-s45m` and `/products/heat-pumps/` goes to `/water-heaters?type=heatpump`. This keeps the site's Google ranking and the old links on Facebook, Lazada and in old emails working. Any other `/product/...` address goes to Water Heaters, and the old sitemap addresses go to `/sitemap.xml`. Product addresses come from `from` in `src/products.mjs`; the other pages are listed in `tools/build.mjs`.

Checked on 2026-11-05 against both live sitemaps: all 48 addresses have a rule, and every rule leads to a page that exists. The redirects only matter to visitors once `dpymi.com.ph` points to this Worker; on the preview link nobody arrives on the old addresses.

**When it becomes the live site:**
- Change `SITE` in `tools/lib.mjs` to `https://www.dpymi.com.ph/` and run the build. This updates the sitemap too.
- Change `<meta name="robots">` to `index,follow`.
- Remove the `X-Robots-Tag` line from `_headers`.
- Allow crawling in `robots.txt` and add `Sitemap: https://www.dpymi.com.ph/sitemap.xml`.
- Add `<link rel="canonical">` back.
- Point the share-image and structured-data URLs at the real domain.
- Set up the form settings above, and make sure every address the site shows exists (see **Email addresses**).
- Turn on Cloudflare Web Analytics and submit the sitemap in Google Search Console.
- Use the Google Maps Embed API (with a key) for Street View.

**Quote list.** "Add to quote" on any product card or product page puts it in a list that follows the visitor across pages (kept in their browser only). The count shows on the "Get a Quote" button, and both quote forms (the homepage's and the contact page's) list the products, tick the matching types and include them in the request. "Get a quote for this" adds the product and goes straight to the form. The finder passes its answers to the form too.

**How the pages are made.** The inner pages are generated by `node tools/build.mjs` from `src/` (one file per page in `src/pages/`, the product data in `src/products.mjs`, the typed spec sheets in `src/specs.json`). The homepage is still the hand-written `index.html`, but the build also writes its header, menu and footer (between the `<!-- @nav -->` and `<!-- @footer -->` markers), so every page has exactly the same ones. The generated `.html` files are committed, so Cloudflare still deploys with no build step. After changing anything in `src/`, `tools/` or the shared files below, run the build and commit the output. `src/` and `tools/` are not published (`.assetsignore`). Links use clean addresses (`/about`, not `/about.html`), which Cloudflare serves directly, so view the pages through a local web server rather than by double-clicking.

**One design, shared by every page:**

| File | What's in it | Used by |
|---|---|---|
| `assets/css/base.css` | Font, colours, type, buttons, the header and phone menu, the footer, Messenger and Viber buttons, the quote list, the "Ask DPY" chat | Every page, the homepage included |
| `assets/css/site.css` | Page heads, sections, product cards, filters, forms, spec tables | Inner pages |
| `assets/js/site.js` | The quote list and the email forms everywhere; on inner pages also smooth scrolling, the header and the scroll reveals (the homepage keeps its own, tied to its GSAP animations) | Every page |

| `assets/js/ask.js` | The "Ask DPY" chat. It builds itself on any page; its links scroll on the homepage and open the right page elsewhere (e.g. "See our clients" opens Projects). | Every page |

**Speed of the inner pages (Lighthouse, mobile, October 2026, local server with compression):** 98–100 on every page checked. How:
- **No stylesheet to wait for.** The build writes the shared styles straight into each page (about 8 KB compressed), so the first paint needs no extra request. `base.css` and `site.css` stay the files you edit.
- **Phones get phone-size photos.** Large photos have a `-800.webp` copy and a `srcset`, so a phone downloads about 30–60 KB instead of 100–200 KB.
- **Nothing hidden that the visitor sees first.** Photos at the top of a page don't wait for the fade-in. The "By building" photos on For Business load after the page settles, and the Contact map loads only once it scrolls into view.
- **Scripts wait their turn.** The chat wakes only when the visitor reaches for it. The chat's markup is already in the page, so nothing shifts when it starts. No script forces a layout while the page is loading.
- **The homepage** scores 97 on the same test (three runs on 2026-11-05: largest paint 2.4 s, blocking time 70 to 90 ms, layout shift 0.002), up from about 81 to 88 in October. What's left is the hero intro and the GSAP animations, which delay the first heater's appearance on a slow phone. Google's PageSpeed test on the live link should be run once more after merging (its free daily quota was used up when we checked).

The homepage keeps inline only what is unique to it (the hero, the 3D tank, the map, the calculator and so on). When the shared styles moved out, its layout was checked element by element at desktop and phone width: identical, apart from the quote list added to its form. `/assets/*` is cached for 30 days, so the build stamps each shared file with a version (`base.css?v=…`). A change reaches returning visitors straight away.

## Performance (checked on Intel UHD integrated graphics)

| Screen | Idle | Scrolling |
|---|---|---|
| Desktop | about 140 fps | about 96 fps |
| Phone size | about 140 fps | about 131 fps |

**Light mode.** On touch screens, PCs with 4 or fewer CPU cores, and data-saver connections, purely decorative loops stop: hero steam, card float, hotspot pulses, heat-wave and drop loops, and step rings. Everything interactive still animates. The chat drop's colour change is now an opacity cross-fade between two ready-made drops, instead of an animated SVG gradient that repainted the always-visible button every frame. On a phone-size screen with the CPU slowed 4×, the idle frame rate went from 32 to about 102 fps and scrolling from 28 to about 66 fps.


How it stays fast:
- **Hero blur:** baked into `hero-steam-soft.webp`, not applied live.
- **Frosted panels:** a pre-blurred copy of the photo, not `backdrop-filter`.
- **3D cutaway:** Three.js no longer loads with the page. It downloads and builds the scene in the first idle moment after the page loads (or earlier if you scroll toward it), so it never stalls a scroll. Shaders compile in the background, shader error checks are off, it's capped at 1.25× resolution, and the render loop stops completely while the tank is off screen.
- **A smooth opening:** the hero intro starts only once the page has painted. The 3D tank builds after the intro and the dial sweep (about 6.5 s in), in small steps. The entrance animations further down are set up in an idle moment after the first paint. The page is re-measured for scroll animations once, after the intro, instead of twice during it. Hidden heaters do not pulse, and the heat waves only move while visible.
- **Native scrolling everywhere.** The smooth-scroll library (Lenis) was removed (October 2026): on Intel UHD it made the browser repaint large parts of the page on every frame. Without it, scrolling the whole homepage draws about 1.5x as many frames (typical frame 7.0 ms instead of 9.7 ms) with fewer slow frames. Chrome already scrolls smoothly with a mouse wheel, and the How It Works tank eases after each wheel step (scrub 0.5).
- **Branch map:** the map library is parsed when the browser is idle, and the fly-in waits until the map is on screen.
- **Scroll work:** entrance animations stop listening to the scroll once they've played. The temperature dial places its knob by maths instead of measuring the SVG path each frame, and plays one intro sweep instead of two overlapping ones.
- **Logos:** the unneeded multiply blending on the brand and client logos is gone (they sit on white cards).

Measured on this PC: the page is ready (DOMContentLoaded) in 0.72 s instead of 1.23 s, the longest start-up freeze fell from 493 ms to 183 ms, and the worst freeze while scrolling on desktop is back to about 70 ms.
- **Loops:** they pause when their section is off screen.
